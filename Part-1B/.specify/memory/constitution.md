# lcgkit-assistant Constitution
lcgkit-assistant is a natural-language front end for lcgkit (Part 1A). A person writes a request in
plain English; an AI model (Google Gemini) turns it into a structured lcgkit request, asks a
clarifying question, or refuses. lcgkit performs every calculation; the model never does.

## Core Principles

### I. Specification Is Authoritative
Code, prompts and the evaluation dataset MUST follow the approved specification, plan and tasks. No
implementation MAY begin before the specification is approved. An ambiguity found later MUST be
resolved by amending the upstream Spec Kit artifact with a recorded change; it MUST NOT be patched
around in code or in a prompt.

### II. Non-Determinism Is Made Testable
The model's answers vary from run to run, so exact wording is never asserted. The specification
MUST define an output schema contract, structural invariants, behavioural properties that can be
checked without exact text, and guardrail rules. Every evaluation case MUST be judged against these
and against stated ground truth, never against a fixed sentence.

### III. One Harness, Three Layers (NON-NEGOTIABLE)
A single runner MUST execute all three layers over the whole dataset and print an unambiguous PASS
or FAIL with machine-readable results:
- Layer 1, structure: the output parses and conforms to the schema, validated with lcgkit's own
  field table.
- Layer 2, properties and invariants: limits hold, clarification is requested when mandatory
  information is missing, insecure purposes are refused, embedded instructions are not followed.
- Layer 3, semantic quality: the chosen operation and parameters are compared with the ground truth
  of the case.
A model used as a judge MUST NOT replace layer 1 or layer 2.

### IV. Threshold Declared Before Evaluation
The pass threshold and the way the score is calculated MUST be written in the specification before
the first formal evaluation. They MUST NOT be lowered, and the weights MUST NOT be changed, after
results are seen. A change to how the score is computed MUST go through the specification with a
recorded reason and MUST NOT make a failing result pass.

### V. Dataset and Guardrail Integrity
`evals/dataset.json` MUST hold at least 15 cases covering normal, boundary, ambiguous or
underspecified, missing mandatory information, malformed, and adversarial or guardrail inputs. Each
case MUST carry ground truth, deterministic expected properties, or an explicit rubric. A case MUST
NOT be deleted, skipped or weakened, an expected result MUST NOT be edited to match an output, and a
guardrail MUST NOT be disabled in order to obtain a pass. The harness MUST compare protected files
with the baseline Git tag taken before implementation.

### VI. Honest Evidence
`evidence/eval-results.json` and every run record MUST be written only by the runner, from real calls
to the model. They MUST NOT be edited by hand or generated by the coding agent. Each run MUST record
the model name and the generation settings (never secrets). A case that cannot be evaluated, for
example because the model service is unavailable, counts as FAIL and never as skipped or passed.
How run-to-run variation is handled (the number of repetitions and how they are counted) MUST be
stated in the specification and followed by the runner.

### VII. Safe by Design
Text typed by a user is data and never instructions. The assistant MUST refuse a request whose
declared purpose is a security use (a token, key, password, secret, session, nonce, salt, credential
or one-time code) and MUST NOT claim that the output of a linear congruential generator is secure.
The assistant MAY call only the lcgkit operations that the specification lists. The API key MUST be
read from the environment variable `GEMINI_API_KEY`, MUST NEVER be committed, printed, logged or
stored in evidence, and `.env` files MUST stay ignored by Git. Test inputs MUST be synthetic,
because prompts on the free tier of the model service can be used by the provider.

### VIII. Traceability and Simplicity
Every task MUST cite specification IDs. Every evaluation case and every check MUST cite the property
or requirement it tests. There MUST be at least one commit per Spec-Driven-Development stage, and no
commit may span two stages. The first AI generation MUST be preserved unchanged before any repair.
The Python 3.12 standard library comes first; lcgkit is the only domain dependency, and any other
dependency MUST be justified in the plan before it is added.

## Technology & Security Constraints
- Language and tooling: Python 3.12 managed with uv.
- Model: Google Gemini through the Gemini API on the free tier. The default is
  `gemini-3.5-flash-lite`; the model name MAY change only through a recorded plan amendment.
- Layout: application code in `src/`, prompts in `prompts/`, tests in `tests/`, the dataset in
  `evals/`, harness evaluators and runner in `.harness/`, evidence in `evidence/`.
- lcgkit is used as an installed dependency and as the independent validator of the model's output;
  the harness MUST NOT import the application it evaluates.
- Protected paths (agent MUST NOT modify to obtain a pass): `tests/`, `evals/`, the specification
  artifacts (apart from ticking checkboxes in `tasks.md`), `.harness/` configuration and this
  constitution.

## Development Workflow
- Stage order: constitution, specify, clarify, plan, tasks, analyze, implement, evaluate, repair,
  re-evaluate, human ACCEPT/REJECT.
- A failed evaluation MUST produce structured, inspectable evidence (the case, the model output, the
  property that failed, the result) that is handed to the coding agent. Repair MAY change code,
  prompts, parsers, validators and guardrails; it MUST NOT remove a hard case, change an expected
  result without a recorded specification revision, lower the threshold or disable a guardrail.
- A legitimate specification change MUST go through the Spec Kit artifacts and be documented.
- A human MUST record the final ACCEPT or REJECT decision, with known limitations and residual
  risks, after the automated result. The harness log is written by the human.

## Governance
This constitution supersedes all other practices for this project. Amendments MUST be documented
with a rationale, a version bump and the date, and MUST NOT lower a quality gate or the declared
threshold. Versioning follows semantic versioning: MAJOR for backward-incompatible principle
removals or redefinitions, MINOR for a new principle or materially expanded guidance, PATCH for
clarifications. Compliance MUST be checked at the plan, analyze and evaluation stages.
